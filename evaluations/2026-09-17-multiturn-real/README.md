# 2026-09-17 多轮真实模型评测与完整 Trace 复盘

本轮只评测、定位和归档，没有修改产品业务代码。主结论：当前单 Agent 能承接聊天、读取 Skill、恢复历史、处理已保存媒体方案，但自然请求到可执行方案、文稿父版本选择、严格交付范围和摘要压缩仍有断点。不是“工具全部失败”，也没有证据支持重建任务调度。

## 运行范围与账目

## 实际上下文：错误信息、噪声、重复与引用

88 次实际请求均保留，没有发现单个 input 数组中完全相同项的重复（0 项）；这只是精确相等检查，不代表不存在语义重复。

1. 初次 CHAT_VERSION 请求估算输入 5,550、工具 4,112，共 9,662 tokens，其中也含当前用户及目录投影，不全是 system。上下文 24,000、生成保留 6,500、摘要安全余量 500，摘要触发线为 `(24000-6500-500)*0.75=12,750`，初始离触发仅约 3,088 估算 tokens。Skill 正文、长回复和 ID 表很快使 3—4 轮开始摘要。估算值不能与供应商实际 token 数混为一谈。
2. 模型反复解释权限、回执和模拟限制，形成语义重复；摘要又按轮记录重复设计细节，压缩效果差。长会话的重复输入是专门压力构造，不能据此推算生产平均成本。
3. 历史搜索回显当前用户与助手刚写出的“我会查历史”，增加自我引用噪声；随后出现工具结果 ID 被当资产 ID 的尝试，属于对象类型理解错误。
4. 最初错误父稿选择时正确原文仍在真实输入，排除“被摘要裁掉导致无法选择”；后来的摘要确实引入/延续错误资产标签，应区分错误发生和传播。
5. 摘要只知道 budget=1800，程序验收包含额外元数据，且以字节保守估算。诊断第 6 轮生成部分估算 1652，补上元数据后仍被拒；多条失败输出供应商实际只有 1006—1578 tokens，但保守估算已超 1800。不是网络超时，不是 JSON 无法解析，而是生成目标与完整对象预算缺少共同口径和有效收缩策略。
6. 已保存媒体对照中每轮都可寻址具体 proposal/receipt；仅文字方案主评测不存在真实对象，不能靠改摘要凭空补出批准对象。
