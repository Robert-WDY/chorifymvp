# Chorify 单 Agent 全流程审计

日期：2026-09-17。当前源码基线：`724ba940add4fe333a55d10f4e15f862106ba800`，分支 `feat/context-agent-20260916`。

本轮分析与离线诊断，没有修改业务代码，没有新调用付费模型、视觉或媒体，没有部署。结论依据用户提供的两张流程图、当前源码、历史真实请求/响应/工具结果/最终 state。建议均未实施，不作为修复完成记录。

## 1. 证据范围与结论

- 23 条真实用例：`context-agent-2026-09-17T03-52-47-518Z`，历史基线 `59ee2ae18330c81a778f98ccdae197fa3bb6aabd`。全量清点请求指标、工具调用和观察材料，重点复核数量、事实、已有方向消费、媒体准备及双图比较链。原运行有真实观察和 2 次图片调用，本轮只读取其记录。
- 多轮真实用例：仓库 `evaluations/2026-09-17-multiturn-real/`，同一历史基线；8 个主会话、2 个诊断会话，48 个实际执行用户轮次，69 次主 Agent 调用、19 次摘要调用。另有 2 个因无可批准方案而未执行的确认步骤，不能计入执行成功。媒体为模拟。
- 当前源码：9 个离线诊断探针，调用真实构造、校验及执行函数，模型/供应商输出注入。只使用隔离的内存会话，不改产品用户数据。循环返回的 `modelCalls` 包含注入适配器调用，不是付费模型调用。
- 不是重新运行全量真实评测；没有重新判断历史图片像素质量；历史缺陷不可直接标成当前复现。

**主要矛盾不是旧任务图没有拆干净。当前入口已经是同一个 Agent 的工具循环。问题集中在：信息跨调用边界没有显式带过去、模型把正确可见信息用错、程序校验只证明局部一致，以及新增校验把不同对象的责任混在一起。**

需要区分三件事：主 Agent 看见资料，不等于观察模型/生成服务看见资料；工具保存成功，不等于保存了用户指定对象；运行 completed，不等于交付符合需求。

## 2. 按两张图核对实际职责

| 环节 | 实际输入与输出 | 决策/执行边界 | 审计结论 |
|---|---|---|---|
| 接收用户输入 | 当前原话、附件、选中资产、交互回答 → 原始记录与资产身份 | 系统保存与检查身份，不解析成旧需求合同 | 当前入口不经过旧 intent/goal-compiler/executor；不能再用旧合同字段解释新 Trace |
| 整理记忆 | 较早完整记录组、前次摘要、有限资产证据 → 有来源的派生摘要 | 摘要不能改原文、批准媒体；不决定业务步骤 | 有连续记忆，但预算目标与固定成本不协调，摘要含引用也不保证语义真实 |
| 构造主模型上下文 | system、注册工具 Schema、目录、可选摘要/资产摘录、近期原文、工具反馈 | 系统裁剪模型视图；原始存储不裁剪 | 关键原文大多可用；目录和 Schema 固定成本高，完整调用参数又不能裁剪 |
| Agent 理解与选择 | 上述上下文 → 回答/一个工具调用/必要问题 | 对象、事实、数量、是否准备方案由 Agent 判断 | 多个历史失败出在这里，不能自动归因于输入丢失 |
| 工具入口检查 | 模型参数 → 类型/归属/原文一致性/批准等检查 | 系统不独立重做完整语义理解 | 拦错误 ID、错类型、错批准有效；不能证明模型选择了正确作品或事实 |
| 观察与生成 | 仅本次明确参数和选中资料 → 观察文字或实际回执 | 不自动继承主 Agent 的整份上下文 | 这是确定的信息传递边界；`materials`、`referenceImages`、`imageId` 都需明确传递 |
| 工具结果回传 | 实际结果 → 有限视图、状态、可回读原记录 ID | 同一 Agent 收到反馈后再做下一步 | 单工具序列成立；没有发现主循环把尚未返回的结果当依赖继续执行 |
| 结果判断与回答 | 用户要求、实际成果、当前回执 → 交付/继续/说明不足 | Agent 负责语义验收，程序做可确定检查 | 数量测量为可选触发，却把一旦声明的要求全轮锁定；当前误拦与漏拦并存 |
| 媒体方案与批准 | 固定参数提案 → 展示 → 选定 ID → 执行固定参数 → 回执 | 按钮由系统直接提交；文字确认由 Agent 判含义、系统验身份 | 冻结、版本、模式、幂等有必要；多次询问普通偏好不是系统门禁要求 |

入口定位：`server/context-agent/index.mjs` → `http.mjs` → `loop.mjs`；媒体复用 `providers.mjs` 的直接客户，不恢复旧 Planner。能力表来自 `runtime.mjs`/`tools.mjs` 实际装配，Skill 只是专业方法。

## 3. 上下文哪里缺、哪里错、哪里只是噪声

### 3.1 观察调用没有继承主 Agent 刚读的资料：确定的跨调用缺口

全量统计：23 条首次主请求均没有遗漏原始记录；18 次成功 `analyze_image`/`compare_images` 的返回记录中 `materials` 全是空数组。统计见 [external-evidence.json](external-evidence.json)。空材料本身不使每次观察错误：只问背景颜色可不需要产品 JSON。但产品事实与卖点分析需要区分资料事实和视觉推断。

`PAR_001` 的实际链路：

1. `read_asset` 返回 `capacity unknown`、`no medical claims` 等正文。
2. 下一次 Agent 调用 `analyze_image`，参数只有图片 ID 和泛化观察问题，没有 `materials`。
3. `tools.mjs` 只解析 `(args.materials || [])`；`providers.mjs` 单独组装视觉请求，不会复制主模型聊天记录。
4. 观察模型推断“更可能是……小容量产品或旅行分装瓶”，同时列出容量、便携性无法确认。
5. 最终回答却将“小容量、直立圆柱形态”列入“可用的形态类卖点”，后面又说容量未知。

这里有两个独立问题：**调用参数未带相关材料**，以及**下游把不确定判断升级成卖点**。前一个修好，不能保证后一个自动消失；主 Agent 自己已经拥有 JSON 和观察中的未知项。

观察结果记录：`b71ae0c5-32f3-4a11-a649-e839c448c510`；最终消息：`562f1ae5-1450-4ecb-b2f4-3c6bf252bead`。

`DEP_001` 同样读到资料、收到观察后，将“无标签”放进“便于定制贴标、分装署名”的已知卖点。没有来源证明这种用途和能力，不是读取失败。把 `no medical claims` 扩成资料明确禁止所有功效，同样是模型对约束范围的扩写，不是上游原文如此要求。

### 3.2 来源登记不等于生成输入：当前实现可直接复现

`sourceIds` 用于血缘和来源冻结；图片服务实际收到 `prompt`、`size`、`referenceImages`，视频服务收到对应提示词/参数/首帧。系统不会读取 `sourceIds` 中的文字并自动拼入 prompt，也不会把其中的图片自动加入参考图。

探针 P6：方案登记 `sourceIds: ['facts','photo']`，注入供应商实际收到 `referenceImages: []`，也没收到产品资料正文；最终资产仍有两个来源 ID。

所以审查要看实际供应商参数，不能用“state 中有来源”证明条件已生效。这里的实现是显式选择设计，不是偷偷丢弃已给 `referenceImages` 的图片；问题是接口容易让人把来源关系当成执行证据。尚未证明某一历史下游缺图就是这条造成，不能倒推。

### 3.3 上下文存在，但对象被错误解释

`CHAT_VERSION` 第 3 轮保存：

- 长版消息 `46a959b4-c317-4721-bfd2-b5b5ef088513`、短版消息 `e9a24e91-496a-4734-ac3f-0126c38ed37c` 的完整原文与 ID 都在实际请求。
- 当时 `omittedRecords=0`，无摘要输入。
- `save_document` 错选短版消息作为父稿；工具据参数成功创建短稿父版本和短稿新版本。
- Agent 称父资产是“长版原稿约110字”。后续摘要又把这个错误标签写进连续记忆。

**首次错是模型对象选择；工具按合法错误参数执行；回答误述实际成果；摘要随后传播错误。** 不能把首错归因于失忆、裁剪或摘要先污染。

当前增加 `sourceText` 和 `parentEvidence` 后，能拒绝“长稿正文配短稿 ID”。探针 P5 证明：如果模型同时选错 ID 与对应短稿正文，仍会成功。工具能验证两者匹配，不能验证这是不是用户说的“原来的长版”。当前改动是证据改善，不是对象选择能力已验收。

### 3.4 检索没有命中，不等于原文不存在

`USER_STYLE_07` 当前窗口已有三个完整方向，用户接着说“用第二个方向”。模型额外做：

`list_assets("脚本 15秒 方向 视频")` → 0；
`search_history("方案 脚本 方向 15秒")` → 0；
`search_history("脚本")` → 找到原方向；仍要求用户证明自己指哪一版。

资产目录不代表聊天作品全集。`list_assets` 按完整 query 子串查名称/ID，`search_history` 按空白分词后要求全部出现，二者都不是语义搜索。当前工具描述没明确说出这个查询语义。P9 用现有函数复现：多加“方案”一个词会把确实存在的方向排除。

最终主请求仍有第二方向完整正文，模型也复述了“手的介入”。所以不是上下文缺方向；是模型过度引入“也许另有更早脚本”的假设，加上对空搜索结果的误读。检索多余且引入反向噪声。

## 4. 模型明明有信息，为什么还会选错

能定位可见行为，不能从 Trace 直接读取模型内部原因。

| 现象 | 能确认的归因 | 不能确认的归因 |
|---|---|---|
| `USER_STYLE_01` 要一个方向给三个 | 用户数量、数量规则都在；最终调用未裁剪；主模型交付不遵从 | 不能断言是某个 Skill 正文导致，该批 23 例没有 `read_skill` |
| `CHAT_VERSION` 保存错父稿 | 两份原文齐全，选错父消息，后续错误命名 | 不能归因于摘要/原稿没传入 |
| `CONFIRM_LANGUAGE` 8 轮没有方案对象 | 零提案调用，把“不能提交生成”过度扩成“不能先保存提案”；模型多次主动询问可默认偏好 | 没有调用执行器，无法归因于供应商失败、依赖死锁或批准接口异常 |
| `SWITCH_FACTS` 新会话先搜历史，再读当前原话 | 读取没有增加必要事实；把工具结果记录 ID 当成资产 ID；曾输出两个调用 | ID 命名空间选错是参数错误，不能说来源资产实际丢失 |
| 观察已有“不确定”，最终仍肯定化 | 事实身份没有约束下游创作内容 | 未做对照，不能说单独换模型/删提示词就必然解决 |

同一历史模型在诊断请求明确要求“用工具保存具体方案”时，能准备两份方案、消费部分批准、拒绝转述授权、替换旧方案并返回原回执。这缩小了故障范围：不是该能力完全不存在，而是自然表达下的动作选择不稳定。诊断同时改变了措辞、明确参数等条件，不是严格 Prompt A/B。

当前默认 `reasoningEffort='none'`、工具名 `generate_image` 实际是准备提案，都是可实验变量。当前提示词已将“准备无需批准”前置，但没有当前基线真实重测，不能声称已治好；也不能仅凭旧失败认定模型能力不足。

## 5. 哪些步骤多余、哪些约束开始变复杂

### 5.1 可以消除的无效往返

- 原文已完整可见仍检索/回读；用资产查空否定聊天作品。
- 为自由创作反复询问色调深浅、尺寸偏好，再另问是否允许准备方案。
- 文字方案、准备许可、可执行方案、执行批准被模型扩成多次确认。流程图只要求具体方案准备 → 批准执行。
- 每个轻任务都带全目录和全工具说明，异常恢复与日常推进一起出现。当前目录已缩短但仍全量索引；仅缩 system 没有消除整个请求的固定成本。

不建议以关键词路由锁死工具或重新加 Planner。先降低当前工具名称/说明与实际动作的歧义，省去不增加信息的读取与提问。

### 5.2 新字数/数量校验混淆了作品与最终聊天

当前 `delivery-check.mjs` 不是完整需求校验：它消费 Agent 自己传给 `measure_text` 的声明，只对声明过的内容起作用。

| 当前诊断 | 实際执行的结果 | 根因 |
|---|---|---|
| P1：不调用测量，直接给两个方向 | 注入模型循环返回 completed | 是否验收仍取决于模型主动选择 |
| P2：用户要40—60字，模型先误报80—120，再改正 | 生效约束变成 min=80/max=60；50字仍被拒 | 程序把模型第一次解释当不可撤销的用户要求 |
| P3：同轮分别测一个标题、三个方向 | 有效 itemCounts 同时为1和3，后次失败 | 要求按轮聚合，没有按实际交付对象区分 |
| P4：正文测过并存稿，最后回“文稿已保存” | 最终说明被正文哈希拦截；固定注入回答持续重复时耗尽4步 | 验收作品内容被扩大为最终聊天的逐字要求 |

P4 证明的是第一次正常状态说明被误拦。耗尽步数是本探针固定重试输出的结果，不代表真实模型必然无法绕开。真实模型可能重测说明或输出全文，但这也不能证明它检查了用户真正收到的保存版本。

`items` 由模型自己划分，两个方向塞进一个字符串并不能靠数组长度识别。因此继续强化“整轮取最严条件、最终原样输出”会增加复杂度，却没有补齐语义数量判断。更合适的是把检查作用于明确成果及版本，并允许对错误声明进行有依据的纠正；这是建议，尚未修改。

### 5.3 要模型重复整份原稿，成本没有被完全计入

当前资产修订要求 `sourceText` 为完整父稿，还要输出完整新稿；工具参数留在模型视图中不可裁剪。保存回执又返回新稿与父稿证据，原文/来源/新稿在不同位置重复。

P7：4000 个中文字符的父稿，调用一次保存只增加末尾句号。真实工具函数在隔离 state 中已建立 v2；下一次主模型上下文构造报 `CONTEXT_BUDGET_EXCEEDED`，第二次决策没发生。截短工具结果无法解决，因为超大调用参数本身被整组保护。

这是**执行后的上下文构造失败**，不是供应商调用失败、依赖顺序错误或写入失败。注入输出绕过了真实模型输出长度限制，因此不能据此声称真实模型能先成功生成那么长的参数；实际使用还可能更早触及输出上限。

完整原文仍须持久保留、需要时可回读。但让模型为已有不可变资产重抄整个父稿，只验证自洽、不能证明语义选对，有显著额外成本。可考虑准确对象/版本与必要片段证据，不应删源文或只留不可读 ID。

## 6. 记忆具体有什么问题

历史 19 次摘要调用中，10 份成功保存，9 次因完整负载超预算失败；LONG_MEMORY 有4次失败。失败没有推进覆盖范围，原文可回读，这个保护是正确的。重启后能答20元，不单独证明摘要保存了20元：近期原文也可能提供答案。

原预算问题：让模型按1800“tokens”生成正文，程序却以整份 envelope 加 sourceRefs 的 UTF-8 估算验收。当前已预留引用/元信息空间、告知字节预算并允许有限重试，是合理改进，但尚无当前真实摘要语义复测。

本轮新增发现 P8：默认24k、预留输出6000、安全500时，可用压力基数17500；目标55%=9625。在图像生成+观察的17工具装配中，**没有任何历史/摘要的固定上下文已估算10969**。删完历史也不能达到目标；加上摘要还更高。75%触发线13125仅比固定底座高2156。

这不构成无限循环：最多调用数、最近两轮保护、失败 hash 等均有限制。但目标不可达，会使程序倾向于持续压缩可压缩历史，增加摘要调用、延迟和证据压缩压力。不能拿“摘要越来越短”解决固定底座过大。

另一问题是证据身份：历史长短稿摘要写进了助手错误声称。当前加入实际 `assetEvidence` 有帮助，但其正文是有限摘录、来源数也有限，校验引用存在仍不等于摘要含义正确。不能把“有sourceRefs”当作事实核验。

## 7. 执行、依赖、素材和校验逐类归因

| 类别 | 本轮发现 | 不应混淆 |
|---|---|---|
| 调用顺序 | 23例中8例双调用被整组拒绝，共16条未执行；恢复为单调用后继续 | 不是两次真实观察，也不是执行器把后步跑在前步之前 |
| 协议一致性 | 当前支持通过配置发送 `parallel_tool_calls:false`，默认不发送；真实供应商能力未核验 | 本轮没改配置，不能说协议已经约束住所有实际请求 |
| 依赖 | 先分析再写Brief/选方向后写脚本存在成功链；失败常是未消费可见上游内容、或未准备下游参数 | 没有证据需要重建任务图、调度器或另一个规划模型 |
| 参数 | 把工具记录ID填进 `read_asset.id`；漏传观察资料；来源关系未落成图片参考参数 | JSON合法不代表字段语义正确 |
| 工具执行 | 已调用的保存/读取通常按参数完成；媒体诊断的冻结执行与幂等能工作 | 工具成功不能替模型判断选稿、数量与事实 |
| 图像编辑 | `IMG_EDIT_002` 有原图观察→edit_image绑定原图→批准→实际v2/parentId→compare_images双图 | 本轮确认链路和输入，不重新声明像素保持合格；比较模型本身仍可能看错 |
| 校验 | 原文与ID一致性、会话归属、版本、批准摘要等结构约束有用；本轮测出交付校验作用范围错误 | 不建议把全部语义重新交给程序猜测 |
| 回答 | 历史会把短稿父资产说成长版，把一条交付追加三条；current completed仍是运行状态 | 前台“本轮回复结束”已与“目标完成”区分，不能只看HTTP200或completed评分 |

素材部分还要分三层：读取元数据 ≠ 视觉观察；视觉观察文字 ≠ 被证实的商品事实；已登记sourceIds ≠ 已进入生成请求。当前比较工具强制两张不同真实图片，图片不会由字符串描述代替，这是应保留的边界。

## 8. 媒体批准流程是否多余

必要且已有实现的步骤：保存固定提案；校验归属、模式、源版本、参数摘要和额度；提交前持久记录；重复批准返回原回执；批次失败/未知后停止余项。这些不该因“简化”删除。

按钮路径在主 Agent 调用前执行冻结方案，再把 system_observation 交给它；文字路径让 Agent 选择 proposalIds，复用同一执行服务。这里没有第二次让模型重新生成媒体参数。

仍要准确描述边界：`approveAndExecute` 校验“来自当前用户消息”和合法方案，不独立判断中文语义是不是肯定授权。若 Agent 把否定误判成批准，不能声称程序还有第二层语义保险。当前转述/否定样例的成功来自模型正确选择不调用确认工具。

`published` 证明方案已发布，`clientRendered` 才是客户端呈现记录，二者都不能证明用户已经阅读。当前代码已标明区别。本轮未重做浏览器交互或实际供应商故障恢复测试。

## 9. 建议优先级与如何证明

| 优先级 | 建议调整 | 验收证据 | 副作用/边界 |
|---|---|---|---|
| P0 | 校验绑定实际交付对象/版本；允许纠正误声明，不把全轮最严要求绑定最终状态话术 | 同轮多作品、保存后回执、误声明纠正、硬约束真的失败应拦；同时检查用户最终拿到的作品 | 需保持“检查后正文不可偷偷变更”，不能简单撤掉全部验收 |
| P0 | 明确主Agent→观察→生成的信息选择接口：必要材料与未知项、实际视觉源显式传递 | 记录实际视觉/供应商请求；断言所需源真的出现；审查最终卖点没升级未知项 | 不把同批所有附件自动注入，避免另一商品串入和更多噪声 |
| P0 | 缩小原稿核验重复输入，兼容长稿；让摘要目标参考不可压缩成本 | 4000字及更长修订的完整反馈循环；不同工具装配下目标可达；真实摘要纠正保真 | 保留原文、版本与回读能力；索引/摘录不能伪装完整原稿 |
| P1 | 自然表达下直接准备提案，去掉准备前普通偏好盘问；解释搜索匹配语义 | 同一输入比较追问数、实际proposal数、错批数、错误来源选择；保留否定与替换测试 | 改名/删说明可能影响兼容，优先模型可见表达，不必改底层执行系统 |
| P1 | 在边界明确之后做受控模型/推理强度/上下文精简对照 | 冻结工具/历史/用户输入、分别改一个变量，记录原始响应和多次重复的语义评分 | 需要单独预算；不凭一次成功决定换模型，不用关键词评分替代审查 |
