# 原稿、摘要与交付验收分阶段修复

日期：2026-09-17。基线：`048f5fb43840f43fc8cf4b4fb78dbcdd9cfa64e8`；分支：`feat/context-agent-20260916`。

保留一个主 Agent：读取上下文、理解需求、选工具、消费结果、判断和回复。没有新 Agent、需求解析器、Planner、业务状态机、每轮语义总审查或媒体后台恢复。工具身份、来源、批准、数量、幂等、版本保护保留。本轮未调用真实文本模型、视觉、媒体或 CLEAR，未部署。

## A：原稿对象与作品正文（专项 3/3）

**原因**：原父版本入口只有 ID。模型对原稿的理解与该 ID 指向的正文不一致时，工具只能照 ID 保存；从聊天归档时又默认整条消息，用户操作说明混入作品。

**实现**：`save_document` 新增 `sourceText`。主 Agent 的新修订必须同时提供准确原稿和 ID；缺失时返回可修复错误。文字与对象不匹配、片段多处重复、已有资产只给部分父稿时不写入。聊天消息可用唯一连续片段作为作品正文，记录来源消息与 UTF-16 范围；持久聊天原话不改。已有资产修订核对完整父稿，父版本不被局部裁剪。回执返回真实 `parentEvidence`，在模型结果正文被裁剪时仍保留父身份、长度、正文片段及回读入口。默认原文索引补充作者、长度及首尾，预算紧张先省略重复索引而非真实消息或反馈。

历史已完成调用的重放仍返回原结果；非模型调用保留原 API 兼容，整条聊天原样存档也仍可用。`sourceMessageId` 未给 `sourceText` 表示完整消息存档；并不是自动猜作品边界。相同消息的不同片段分别保存，只复用相同正文的原稿。三个既有脚本调用夹具补充原文参数，原有业务 expected、父关系、调用次数断言全部保留。

**证据**：[原稿身份 Trace](traces/A-source-identity.json)、[历史错误父稿回放](historical-replay/parent-replay.json)、[历史指令包装回放](historical-replay/body-replay.json)。归档 CHAT_VERSION 的旧模型修订参数现在因缺少原文被拒；提供正确原文但保留错误 ID 被拒；改为正确 ID 后正文与父版本对应。LONG_MEMORY 原文包装仍完整存于历史，父作品只保留准确正文。另测 SQLite 重启、幂等、磁盘失败回滚及片段去重。

**边界/副作用**：修订调用多传一次原文，增加 token；片段重复须提供更完整原文。程序证明 ID 与声明原文一致，不能单独证明模型选中了用户真正所指的对象。历史回放由测试明确提供预期原文，不是模型自主修正证明；真实模型选择仍待验收。

## B：摘要预算与对象身份（专项 3/3）

**原因**：之前把 1800 同时当作模型可输出目标与含服务端身份/引用的完整摘要预算；按字节估算验收时超限。摘要又可能复述助手给错误对象的标签，而没拿到资产实际正文。

**实现**：沿用当前估算方法和完整预算，先为身份、引用、JSON 转义预留空间，明确给模型正文 UTF-8 字节目标及最多 8 个来源引用。预算失败时附实测超限反馈，将正文目标收至前次 60%，在原单轮摘要配额及共享模型预算内重试；默认最多两次，不另增加预算。协议、来源、网络和存储失败不重试，不推进覆盖。相同失败源区间没有新信息不重复调用。要求合并旧摘要与新增记录，而非逐轮追加日志。

摘要输入及主 Agent 的摘要视图增加受限的实际资产证据，最多 8 项、1000 估算 token：正文/长度、来源、父版本、版本号及回读入口。正文超长明确截取，不把模型标题当成身份事实，也不将截取内容当完整原稿。用户新纠正仍优先，实际证据用于纠正摘要的对象标签，不自动改写业务事实。

**证据**：[两次限额压缩及输入](traces/B-budget-and-identity.json)、[历史预算对照](historical-replay/summary-budget-comparison.json)。模拟首次超限、第二次按缩小目标成功；完整结果在预算内、原文未变。连续失败最多两次、覆盖不推进，再次运行同源零重试；非法引用/网络故障各一次结束。实际短稿正文进入摘要请求和下一次主 Agent 请求。历史预算对照使用历史模型输出和新构造身份 envelope 计算，不是重新生成摘要。

**边界/副作用**：保留原文和回读机制，最多 8 项引用会使摘要引用更集中；限次重试可能占用本轮第二个摘要额度，但保留主调用预算。实际模型能否准确压缩、纠正错误标签、长期记住新事实，仍未验证。供应商 token 数与此保守估算不混用。

## C：已声明硬要求与实际交付一致（专项 5/5）

**原因**：测量结果只给 Agent 参考，与最终发出的文本没有关联；正文合格后再加备选/说明仍可结束。没有全量交付覆盖检查。

**实现**：复用 `measure_text`，新增可选 `requirements`（字数上下限/交付项数）、`bodyText` 和 `items`。Agent 识别要求和每项语义，程序检查数字及覆盖：正文必须真实存在于完整 text；items 以双换行拼接必须严格等于完整 text，不能漏掉备选。字数只算指定正文，不把标题计入。回执保存通过/失败和文本指纹。

最终无工具回复只核对本轮已有测量回执。失败或文本变化不写成已完成 assistant 消息，记录实际 `system_observation`，由同一个 Agent 消费反馈并局部修正/重测。没有第二次独立语义模型审查。反复不修复耗尽原预算后如实结束，不伪造合格。普通无约束对话不强制测量，不跨用户轮次继承旧测量。检查状态是运行层活动，不伪装成模型选择的新工具调用。

**证据**：[追加备选后的拦截与恢复 Trace](traces/C-final-drift.json)。测试覆盖 items 漏项、数量不符、正文不足、标题不计数、不存在的正文、测量后追加、失败后只做无约束测量试图绕过、正确重测、跨轮无约束对话和非法测量不放行；完整原模型输出留在 Trace，错误最终稿不写成正式交付消息。

**边界/副作用**：自然语言要求是否被识别、一个 item 是否真实只含一个方向/一句话，仍由 Agent 判断，不能靠数组长度证明语义正确；模型完全漏调用测量时没有程序合同可核对。这是已声明要求到实际文本的闭环，不是所有用户要求自动验收。严格指纹要求合格后不能再加客套话；新内容需重测，可能增加一次工具/主调用。流式片段仍可能提前可见，但失败后明确标为未通过，不表示已完成交付；其他已保存文件不回滚。
